00 · El reto

Una primera conversación, no un asistente completo

PartyQuest es una aplicación de práctica para conversar con Pachi, un personaje que ayuda a explorar ideas de planes. El objetivo de D1 es recorrer un ciclo pequeño: escribir un mensaje, enviarlo a la API propia, solicitar una respuesta al modelo y mostrarla. El ciclo permite estudiar fronteras y contratos; no convierte por sí solo a Pachi en guía local confiable.

La plantilla visual ofrece una base de presentación. El comportamiento se desarrolla en incrementos: conexión, estados, consumo, instrucciones y contexto local de interfaz. Ver una pantalla atractiva no demuestra que el chat funcione; ver una respuesta tampoco demuestra que provenga de una conexión real ni que sea correcta.

Tres afirmaciones distintas

Funciona: la aplicación y la ruta completan el ciclo esperado. Conectividad real: una llamada llegó al proveedor y regresó, con la configuración autorizada. Calidad: la salida es útil, pertinente y confiable para un propósito. Una prueba simulada puede demostrar el contrato de la primera; no demuestra la segunda ni la tercera.

En D1 no hay memoria del modelo: cada envío contiene el mensaje actual, no los turnos visibles anteriores. No hay catálogo consultado, recuperación de documentos (RAG), herramientas, streaming ni persistencia conversacional. Las burbujas anteriores pueden seguir en pantalla, pero no son contexto del modelo.

Actividad y comprobación

Dibuja el ciclo que esperas observar y marca qué evidencia confirmarías en cada paso. Después, explica en una frase qué puede probar una pantalla estática, qué prueba una respuesta obtenida con fake y qué requiere una llamada real. ¿Qué queda fuera del alcance aunque Pachi parezca seguro de sí mismo?

01 · D1·B1

Las piezas de una aplicación con IA

Modelo, proveedor y producto

Un modelo de lenguaje calcula una continuación probable a partir de los tokens que recibe y de las instrucciones que lo acompañan. No es una base de datos que garantice hechos; puede generar una frase plausible y equivocada. El proveedor opera el servicio que ofrece el modelo. La aplicación decide qué pedir, qué datos compartir, qué validar y cómo representar el resultado. Son responsabilidades diferentes.

Un agente de desarrollo es una herramienta que ayuda a una persona a explorar o modificar un proyecto; el chatbot que se construye es otro producto, con usuarios, datos y límites propios. Autorizar a un agente a editar localmente no equivale a autorizarle una publicación, acceso remoto o uso de credenciales.

El recorrido mínimo

El navegador presenta la interfaz React. Envía JSON a la API propia, servida con Hono. La API valida datos, crea la solicitud para Groq y devuelve un resultado público. Solo la API habla con Groq. El núcleo de la lógica debe poder expresar reglas sin depender directamente de React, Hono ni el SDK de Groq; las herramientas de framework y proveedor quedan en los bordes. Organizar por funcionalidades ayuda a ubicar responsabilidades; no hace falta inventar capas vacías.

Frontend y API son aplicaciones y procesos distintos, aunque vivan en un mismo repositorio, workspace o máquina de desarrollo. Un workspace agrupa paquetes y comandos; no convierte al navegador en servidor ni hace seguro un secreto.

Comprobación útil: GET /api/health puede responder {"status":"ok"} si la API está en ejecución. No llama al modelo y no revela si Groq está configurado. Health demuestra disponibilidad de esa ruta local, no una llamada real.

Crear y conectar con cuidado

El proyecto parte de una carpeta y una base de presentación; incorporar plantillas no significa que el comportamiento esté terminado. Revisa qué archivos pertenecen a cada aplicación y qué comandos arrancan cada proceso. MCP es un protocolo para conectar herramientas y fuentes: una conexión puede recibir permisos y compartir información. Antes de activarla, entiende su alcance. Conectar MCP o preparar una cuenta de Vercel no autoriza despliegues; en este bloque se prepara una cuenta personal de Vercel; conectar el agente es opcional y no se publica nada.

Actividad: dibuja el camino de Health y tacha navegador de modelo, Groq y proveedor: ¿cuáles participan? Salida: ¿qué observación te falta para afirmar que una solicitud llegó al modelo?

02 · D1·B2

Un mensaje cruza fronteras

HTTP, JSON y validación

HTTP define solicitudes y respuestas con método, ruta, encabezados, cuerpo y código de estado. JSON representa datos estructurados; que un texto pueda analizarse como JSON no significa que cumpla el contrato esperado. TypeScript ayuda durante el desarrollo, pero un dato externo debe validarse en tiempo de ejecución: quien llama puede enviar cualquier forma.

La única solicitud pública de chat es POST /api/chat con un objeto JSON que tenga exactamente {"message":"…"}. El servidor recorta espacios al inicio y al final. El resultado no puede quedar vacío y admite hasta 2.000 puntos de código Unicode, inclusive. Cualquier propiedad adicional —como history, messages, system, model o location— se rechaza. Una entrada inválida produce 400 invalid_request antes de consultar la configuración o llamar al proveedor.

El límite cuenta puntos de código Unicode, no grafemas percibidos por una persona. Por ejemplo, una letra acentuada puede representarse como un punto precompuesto o como letra más marca combinante; el emoji familiar puede componerse de varios puntos. En JavaScript, String.length cuenta unidades de código UTF-16, por lo que ciertos caracteres fuera del plano básico cuentan como dos. Ni length ni el número de grafemas equivalen siempre a puntos de código: la implementación debe usar la unidad especificada por el contrato.

Clave y datos mínimos

GROQ_API_KEY y GROQ_MODEL viven en el servidor. El modelo de D1 es openai/gpt-oss-20b. Un archivo .env sirve para configuración local, no es cifrado ni un mecanismo de control de acceso. El ejemplo .env.example contiene nombres y valores claramente falsos.

Una clave no debe aparecer en código del navegador, bundle, solicitudes de red desde el navegador, respuestas, capturas ni registros. El cliente no decide instrucciones system, modelo, historial o ubicación. La API puede arrancar sin configuración de Groq; el endpoint de chat comunica el problema al ser solicitado. La respuesta exitosa expone el identificador público del modelo, no la clave.

Contrato de éxito y evidencia

Una respuesta 200 incluye reply no vacío, model y usage (objeto o null). Una llamada válida provoca exactamente una llamada al proveedor con el mensaje de sistema definido por el servidor y el mensaje actual ya recortado. Una solicitud inválida provoca cero llamadas.

Para desarrollar una prueba repetible se sustituye el proveedor por un fake controlado. Se observa la interfaz HTTP pública: estado, cuerpo, llamadas y datos enviados. El fake demuestra cómo se comporta la API ante respuestas simuladas; no prueba credenciales, conectividad ni disponibilidad de Groq. Una llamada real manual requiere configuración y autorización propias, y es evidencia distinta.

Actividad: anota qué cruza cada frontera en navegador → API → Groq → API → navegador. Marca explícitamente que ubicación e historial no viajan. ¿Por qué una prueba con fake no acredita conectividad real?
03 · D1·B3

Medir sin inventar

Tokens y datos incompletos

Un token es una unidad de segmentación del modelo; no equivale a una palabra. El proveedor puede informar tokens de entrada, salida y total. La API normaliza cada valor como entero no negativo o null si falta o no es válido. Si no informa ninguno, usage es null. No se calcula un valor ausente a partir de los otros ni se inventa un cero.

La ausencia de usage no invalida una respuesta utilizable: la interfaz conserva reply y marca el consumo como no disponible o incompleto. Un cero significa que se informó un valor real de cero; null significa desconocido. Mostrar cero cuando falta información falsea la observación. La interfaz puede mostrar el consumo por interacción y acumular lo observado en la conversación visible; si faltan datos, debe señalar la incompletitud también en el acumulado.

Estimación no es factura

Para estimar se necesitan los tres valores de usage (entrada, salida y total, conforme a la regla del contrato de contar los tres) y una tarifa documentada y vigente para el modelo. La fórmula usa entrada y salida; el total permite comprobar el conjunto informado, pero no sustituye un componente faltante:

costo_estimado = (tokensEntrada × tarifaEntrada
                + tokensSalida × tarifaSalida) / 1.000.000

La fórmula supone tarifas expresadas en moneda por millón de tokens. Anota moneda, unidad, fecha de consulta y modelo. Si falta cualquiera de los tres valores, no presentes una estimación. La API no calcula el costo ni conoce tarifas. Un cálculo teórico tampoco es la cuota gratuita ni una factura: políticas, caché, redondeos y tarifas pueden cambiar.

Hoja ficticia: ejercicio, no precio vigente

Supongamos, solo para practicar, una tarifa inventada de 0,20 unidades ficticias por millón de tokens de entrada y 0,80 por millón de salida. Si la observación contiene 12.000 tokens de entrada, 3.000 de salida y 15.000 en total:

(12.000 × 0,20 + 3.000 × 0,80) / 1.000.000
= (2.400 + 2.400) / 1.000.000
= 0,0048 unidades ficticias

Si el total no estuviera informado, aunque se pudiera sumar entrada y salida, el contrato indica no completar el campo faltante ni hacer esta estimación. El ejercicio muestra la disciplina de etiquetar supuestos, no el precio de Groq.

Errores como parte del producto

Los errores usan un sobre JSON con error.code, message técnico y retryable. La interfaz decide por code; no muestra message, trazas, secretos ni contenido crudo del proveedor. La matriz exacta:

codeHTTPretryableSignificado y efecto
invalid_request400falseCuerpo inválido; validar antes del proveedor.
configuration_error503falseFalta clave o modelo, o credencial/modelo no aceptado.
quota_exceeded429falseLímite de uso o tasa; no se promete cuándo vuelve ni se ofrece «Reintentar».
provider_error502trueFallo de comunicación/proveedor o texto no utilizable; recuperación manual posible.
internal_error500trueFallo inesperado de la API; recuperación manual posible.

Con un error recuperable se ofrece «Reintentar» y «Editar mensaje» cuando retryable es verdadero. Para errores con false, se ofrece editar, sin reintentar. Error de red o respuesta que no cumple el contrato se trata como fallo recuperable, sin detalles técnicos. El 429 del proveedor se normaliza como quota_exceeded; no se distingue límite por minuto de cuota diaria. D1 no aplica reintentos automáticos ni timeouts de incrementos posteriores.

Actividad: describe lo que vería la persona con respuesta válida pero usage parcial y con 429. ¿Por qué desconocido no es cero? ¿Qué acción sería engañosa prometer después de una cuota agotada?

04 · D1·B4

Roles, instrucciones y límites

El modelo recibe mensajes etiquetados por rol. system contiene instrucciones definidas en el servidor; user expresa el mensaje actual; assistant representa respuestas del modelo. Los roles organizan el contexto enviado, no prueban la verdad de su contenido.

En D1, la API envía las instrucciones del servidor y el mensaje actual. Los intercambios que permanecen visibles en la interfaz no se envían como historial. La ventana de contexto limita cuánto cabe en una solicitud; no es memoria permanente entre solicitudes ni entre recargas.

Diseñar y comparar prompts

Una instrucción puede separar objetivo, tono, formato, restricciones y criterios de calidad. En zero-shot se describe la tarea sin ejemplos; en few-shot se añaden ejemplos representativos. Dividir una tarea en pasos observables puede facilitar la respuesta. Pedir una explicación breve y verificable puede ayudar a entender una conclusión, pero no debe confundirse con prueba de verdad ni solicitar el razonamiento interno privado del modelo.

Para comparar, conserva idéntico el mensaje de prueba y cambia una sola instrucción. Registra qué cambió de manera observable, no solo cuál salida gustó más. La salida es variable; un resultado favorable no garantiza la siguiente respuesta. Una redacción amable puede contener una alucinación o información desactualizada. En D1 Pachi no consulta catálogo ni verifica recomendaciones locales; no presentes sus sugerencias como comprobadas.

Actividad: escribe dos instrucciones distintas para un mismo mensaje hipotético. Define antes qué rasgo observarás —por ejemplo formato o claridad— y qué no puedes concluir de una sola muestra. ¿Puede una respuesta clara y cordial ser falsa?
05 · D1·B5

De la intención a evidencia comprobable

Una plantilla útil

Una petición acotada distingue objetivo, contexto necesario, restricciones, formato y criterio de aceptación. Las variables que aporta una persona no deben confundirse con instrucciones fijas del servidor. No incluyas secretos en prompts ni des al agente de desarrollo una solicitud abierta que abarque tareas futuras.

SDD, ODD y TDD

SDD expresa comportamiento observable antes de construir. ODD explora el alcance, resuelve decisiones pendientes y autoriza un incremento delimitado. TDD observa primero una prueba fallida (RED), implementa lo mínimo para hacerla pasar (GREEN) y refactoriza conservando la prueba. El contrato público es la referencia de comportamiento; probar detalles internos por comodidad puede dejar sin comprobar lo que observa quien usa la API.

Una prueba determinista controla el proveedor, envía solicitudes a la interfaz HTTP pública y observa estado, cuerpo, llamadas y ausencia de filtración de secretos. Un smoke test real comprueba otro aspecto: una llamada efectiva con configuración real autorizada. Ninguno por sí solo evalúa de manera suficiente la calidad general del modelo.

Qué debe distinguir una prueba

  • Objeto exacto y válido frente a JSON inválido, tipos incorrectos, propiedad adicional y mensaje vacío.
  • 2.000 puntos de código Unicode válido y 2.001 inválido; verificar que la entrada rechazada no llama al proveedor.
  • Validación de entrada antes de configuración, clave/modelo ausente, proveedor simulado y usage total o parcialmente ausente.
  • Status, sobre JSON y llamada única en éxito; cero llamadas para solicitud inválida.
  • Que una clave de prueba no aparezca en respuesta ni mensajes de error.

La prueba no debe depender de una clave real. Tampoco debe afirmar conectividad real si el proveedor es fake. Mantén separados el fallo esperado de una regla y el resultado de las demás: una respuesta visualmente correcta no compensa un estado HTTP equivocado.

Actividad: redacta un criterio y una tabla de casos sin escribir la implementación. Incluye entrada, respuesta esperada, llamadas al proveedor y qué dato no debe filtrarse. Pregunta de salida: ¿qué cambio incorrecto haría fallar tu prueba?
06 · D1·B6

Conectar la interfaz y cerrar el ciclo

Estados y recuperación

La interfaz distingue vacío, mensaje listo, solicitud en curso, respuesta y error. Durante la solicitud comunica «Revisando opciones…». No inicia reintento automático ni impone el timeout de incrementos posteriores. Cuando corresponde, permite corregir el mensaje o iniciar un reintento manual; ante cuota agotada, explica el límite sin botón de reintento ni promesa de disponibilidad.

El error debe dejar claro que el intercambio anterior sigue visible en esta página y si la persona puede editarlo. No se presentan mensajes técnicos del proveedor. Si la red falla o la respuesta no respeta el contrato, se trata como fallo recuperable con copy seguro.

Ubicación y consentimiento

El navegador puede solicitar permiso para obtener coordenadas; la persona puede rechazarlo y el dispositivo puede fallar o no disponer del servicio. Debe existir alternativa de escribir una zona. Coordenadas capturadas no equivalen a cobertura conocida, distancia calculada o recomendación verificada. En D1 la ubicación —capturada o escrita— permanece solo en la interfaz: no viaja a la API ni al prompt.

Lo visible no equivale a memoria

Mientras la página está abierta, la interfaz puede conservar mensajes, ubicación o zona y datos de consumo. Eso no los envía al modelo. Al recargar, la conversación se pierde; la apariencia del shell puede persistir por diseño, pero no el intercambio conversacional.

«Nuevo plan» solicita confirmación. Si se confirma, limpia intercambios, ubicación/zona y consumo de la conversación. Si se cancela, conserva el estado. No revoca el permiso del navegador ni cambia la cuota. Un reinicio local tampoco borra registros o datos de sistemas externos; no hay persistencia conversacional que borrar en D1.

Actividad: recorre éxito, error de proveedor, cuota, permiso denegado, nuevo plan cancelado y confirmado, y recarga. Para cada uno, indica qué permanece visible, qué se limpia y qué datos salen del navegador. ¿Dónde reside cada dato y cuánto tiempo?

07 · Cierre

Autoevaluación: explica el recorrido

  1. Dibuja navegador, API y proveedor; ubica la clave y describe la solicitud mínima.
  2. Explica por qué Health no demuestra una llamada al modelo y por qué un fake no demuestra conectividad real.
  3. Describe el límite de 2.000 puntos de código y por qué JavaScript String.length no es necesariamente esa medida.
  4. Interpreta usage ausente, parcial y cero informado sin confundirlos; enumera qué se necesita para estimar costo.
  5. Explica la diferencia entre cuota, estimación y factura, y qué respuesta corresponde a 429.
  6. Justifica cómo comparar prompts sin convertir una salida plausible en verificación.
  7. Explica qué cubre una prueba pública determinista y qué no; identifica cuándo no se llama al proveedor.
  8. Separa los intercambios de la interfaz del contexto enviado al modelo y describe reinicio y recarga.

Si una respuesta no puede justificarse con una observación, anótala como pregunta, no como hecho. Catálogo, recuperación, ubicación en solicitudes y memoria pertenecen a incrementos posteriores, no a esta primera conversación.
